# 200MB asset read — capacity baseline

**Date:** 2026-09-16 · **Target:** self-hosted MinIO on k3s (`friday`) · **Generator:** k6 0.58.0, in-cluster Job

Establishes the ceiling tanukistore's `/download` route (spec 4.7) will inherit,
using the payload profile it actually has to serve: a 200MB Electron bundle.

## Setup

| | |
|---|---|
| Node | `friday`, 16 cores, 62GB RAM, NVMe, k3s v1.34.4+k3s1 |
| MinIO | standalone, 1 replica, 1 drive, `local-path` PVC (5Gi) |
| Object | `tanukistore-assets/asset-200mb.bin`, 209715200 B of `/dev/urandom` |
| Path | k6 Job → ClusterIP Service → MinIO pod. Nothing leaves the node. |

The load generator runs **inside** the cluster. A NodePort would put the host
network in the measurement path, and `kubectl port-forward` would be worse — a
single userspace proxy that saturates well before MinIO, turning every number
into a measurement of port-forward. In-cluster is also the path
tanukistore-server will take.

## Saturation curve

Per-plateau steady state, ramps excluded:

| Concurrency | Requests | req/s | Aggregate MiB/s | Per-stream MiB/s | Scaling |
|---|---|---|---|---|---|
| 1 VU | 125 | 3.29 | 658 | 658 | — |
| 4 VU | 499 | 13.13 | **2626** | 657 | **×3.99** |
| 8 VU | 505 | 13.29 | **2658** | 332 | ×1.01 |
| 16 VU | 448 | 11.79 | 2358 | 147 | ×0.89 |

**The knee is between 4 and 8 concurrent streams, at roughly 2.6 GiB/s.**

- Scaling to 4 VUs is almost perfectly linear (×3.99 on 4× the concurrency) —
  nothing is contended yet.
- 4 → 8 buys **1%**. This is the ceiling.
- 8 → 16 is *negative* (×0.89): aggregate throughput falls while per-stream
  collapses 658 → 147 MiB/s. Past the knee, extra concurrency only divides the
  same bandwidth into slower streams and adds contention.

The practical reading: admitting more than ~8 concurrent 200MB downloads does
not serve more bytes per second, it just makes every client slower. That is an
argument for bounding in-flight asset transfers rather than letting them queue.

## Caveats

1. **Page cache, not disk.** One 200MB object read repeatedly on a 62GB box is
   served from RAM after the first read. Real traffic spans many distinct
   assets and will hit NVMe, so treat 2.6 GiB/s as the *serving-path* ceiling
   (MinIO + CNI), not a storage benchmark.
2. **No network hop.** Traffic stays on the node. A real client pulls over the
   LAN/WAN, which will be the binding constraint long before 2.6 GiB/s — 1GbE
   caps at ~119 MiB/s, i.e. ~22× below this ceiling.
3. **Anonymous GET.** The bucket is public-read so k6 could issue a plain GET
   instead of implementing SigV4. Production must keep assets private behind
   presigned URLs; signing overhead is not measured here.
4. **Standalone MinIO.** Single drive, no erasure coding. Distributed MinIO
   trades throughput for durability and would measure differently.
5. This is MinIO direct. tanukistore-server is not yet implemented, so its own
   overhead — cache tiers, redirect vs proxy — is not in these numbers.

## Reproducing

```sh
kubectl -n tanukistore create secret generic minio-credentials \
  --from-literal=root-user=tanukistore \
  --from-literal=root-password="$(openssl rand -base64 24)"
kubectl apply -f deploy/minio/minio.yaml
kubectl apply -f deploy/minio/seed-job.yaml

kubectl -n tanukistore create configmap k6-scripts \
  --from-file=loadtest/minio-200mb.js --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f deploy/minio/k6-job.yaml
kubectl -n tanukistore logs -f job/k6-minio-200mb
```
